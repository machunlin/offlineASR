# 优化调整建议报告

> 评审对象：`fix/asr-windows-hardening`
> 评审提交：`b8ee67ce9655cfa5a8254031c29237b315011e1c`
> 评审日期：2026-11-26
> 需求基线：《项目设计文档V2.md》V2.2（Java/Spring Boot 路线）
> 说明：本报告基于实际部署、REST 调用、浏览器烟测和 Windows CI 结果提出；本轮未修改业务代码。

## 一、总体结论

**当前分支不建议直接作为可发布版本交付。** 核心 ASR、模型加载、原生 JNI、后端识别和前端 JavaScript 合同在 macOS ARM64
上可运行，但仍有以下阻断项：

1. macOS 启动脚本本身语法错误且不可执行。
2. 代码把录音上限改为 60 秒，与需求文档的 600 秒基线冲突。
3. HTTP 错误契约与 Servlet 层实际上传限制不一致。
4. 推理超时和请求总超时未实现，需求仍有缺口。
5. Windows 服务配置、发布包内容和哈希覆盖未闭环。
6. Chrome 真麦克风、5 条真实普通话样本、断网和 Windows 目标机仍未经实机验证。

## 二、阻断级问题（发布前必须处理）

### P0-1：`scripts/mac-start.sh` 无法执行

证据：

- 文件权限为 `100644`，没有可执行位。
- 第 3 行 `ROOT="$(...` 缺少闭合引号，`bash -n scripts/mac-start.sh` 报 `unexpected EOF while looking for matching '"'`。
- 直接执行 `./scripts/mac-start.sh` 返回 `permission denied`。

建议：

1. 修复第 3 行引号并设置可执行位。
2. CI 增加 `bash -n scripts/mac-start.sh` 和实际启动 smoke test。
3. 在 README 中区分“手工 `java -jar` 验证”与“交付脚本验证”。

验收标准：干净工作区中执行 `./scripts/mac-start.sh` 能启动服务，健康检查返回 READY。

### P0-2：录音时长基线不一致

证据：

- 需求 V2.2 仍规定单次录音最长 10 分钟，V1 配置基线也是 600 秒。
- `AsrProperties`、`application.yml`、前端倒计时和测试用例被改为 60 秒。
- Windows 外部配置 `deploy/windows-x64/config/application.yml` 仍是 600 秒。
- 实测当前 macOS 默认包：60 秒 WAV 成功，61 秒 WAV 返回 422；这说明是 60 秒实现，而不是 600 秒实现。

建议：

1. 先确认需求到底应保留 600 秒还是正式变更为 60 秒。
2. 若保留 600 秒，恢复后端默认值、前端上限和文档/测试用例，并增加 600 秒边界测试。
3. 若正式变更，先更新需求文档版本和变更记录，再统一所有配置与文档，不能只改代码和页面。

验收标准：需求、前端、后端、Windows 外部配置、WinSW 环境变量和测试用例使用同一个上限值。

### P0-3：HTTP 错误契约未落实

实测结果：

| 请求                     | 当前结果                       | 需求结果                          |
|--------------------------|--------------------------------|-----------------------------------|
| 非 multipart / 缺少 file | HTTP 500 `ASR_FAILED`          | HTTP 400 `INVALID_REQUEST`        |
| 51 MB 上传               | HTTP 500 `ASR_FAILED`          | HTTP 413 `FILE_TOO_LARGE`         |
| 非法媒体文件             | HTTP 422 `AUDIO_DECODE_FAILED` | HTTP 415 `UNSUPPORTED_MEDIA_TYPE` |

证据：

- `MaxUploadSizeExceededException` 和 `MultipartException` 被 `GlobalExceptionHandler(Exception.class)` 统一落成 500。
- 当前 `AsrService` 的上传大小检查发生在 controller 进入之后，无法覆盖 Servlet 层提前拒绝的请求。
- 单个超限请求实测触发 22 次 `MaxUploadSizeExceededException` 完整堆栈记录；单个非 multipart 请求触发 11 次
  `MultipartException` 记录，日志文件短时间增长到约 293 KB。

建议：

1. 显式处理 `MaxUploadSizeExceededException`、`MultipartException`、`MissingServletRequestPartException`。
2. Servlet 层拒绝也必须返回统一的 `success/errorCode/message` 结构。
3. 区分“媒体无法识别”和“媒体可识别但解码失败”，避免所有 FFmpeg 非零退出都映射成 422。
4. 对已知客户端错误只记录一行 WARN，不记录完整堆栈，避免日志放大。
5. 增加真实 HTTP integration test，不只用 MockMultipartFile 单元测试。

验收标准：上述请求分别稳定返回 400/413/415，且单次请求只产生一条可预期错误日志。

### P0-4：推理超时和请求总超时仍未满足需求

需求要求闸门获取、解码、推理和整个请求都有明确超时与错误码。当前分支移除了 `inferenceTimeoutSeconds`，也没有
`ASR_REQUEST_TIMEOUT_SECONDS` 或总请求时限实现。

合理之处是：同步 JNI 调用不能安全中断，这个判断正确；但不能因此把需求项静默删除。建议：

1. 由项目负责人正式批准“JNI 同步推理不设可中断超时”的偏差，并写入需求变更记录；或
2. 增加进程隔离、请求级 watchdog、可取消推理方案等工程措施；或
3. 至少增加总请求兜底超时和明确的运维告警，而不是无限等待。

验收标准：需求、实现和测试对推理超时能力给出一致说明，不能用不存在的配置项伪装已支持。

## 三、高优先级功能问题

### P1-1：健康检查和监控字段不完整

实测 `/api/asr/health` 返回 `applicationStatus`、`modelLoaded`、`modelName`、`inferenceDevice`、`inferenceThreads`、
`ffmpegAvailable`、`uptime`，但没有需求列出的 `modelVersion`；模型加载耗时也没有结构化暴露。Actuator 指标已提供
`process.cpu.usage`、`system.cpu.usage`、`jvm.memory.used` 等，可继续保留。

建议：补充 `modelVersion`、模型加载耗时和明确的有效配置字段；只在本机诊断模式开放 metrics。

### P1-2：前端缺少需求要求的展示与取消能力

页面当前有开始、结束、清空、状态、60 秒倒计时和结果。需求还要求：

- 显示录音时长；
- 显示识别耗时；
- 显示系统状态；
- 录音过程中允许取消；
- 对设备不存在、权限拒绝、设备占用给出更明确提示。

当前 `app.js` 虽把 `inferenceSeconds` 放进事件 detail，但没有显示到页面；没有取消录音控制；页面也没有主动请求健康状态。建议补齐
UI 和 JS 合同测试。

### P1-3：FFmpeg 进程和错误输出处理不完整

需求明确要求检查 FFmpeg 错误输出。当前生产启动器把 stderr 设为 `DISCARD`，失败日志只显示 `exitCode`；非法媒体实测只能看到
`FFmpeg decoding failed exitCode=183`，无法判断真实原因。超时分支 `destroyForcibly()` 后没有等待进程退出，中断分支没有销毁进程，Windows
上可能造成文件句柄占用和临时文件清理失败。

建议：有界采集 stderr 尾部并写入本机日志；超时、中断和异常路径统一终止并 `waitFor`；增加进程生命周期测试。

## 四、Windows 交付问题

### P1-4：外部配置和 WinSW 服务会改变有效上限

证据：

- `deploy/windows-x64/config/application.yml` 仍为 `max-duration-seconds: 600`。
- `scripts/offline-asr.xml` 没有设置 `ASR_MAX_DURATION_SECONDS`。
- 前台 `windows-start.bat` 设置 60，因此前台和服务模式行为不同。
- 以外部配置启动且不设置环境变量时，Actuator 实际读回 `600`。
- 外部配置硬编码 `server.address: 127.0.0.1`，实测即使设置 `ASR_HOST=0.0.0.0`，Tomcat 仍只监听 127.0.0.1，文档中的覆盖说明不成立。

建议：统一使用 `${ASR_MAX_DURATION_SECONDS:...}` 和 `${ASR_HOST:...}`，不要重复硬编码；或在 WinSW XML
中显式设置同一套环境变量。发布前用服务启动方式读回有效配置。

### P2-1：新增诊断脚本未进入发布包

`windows-diagnose.bat` 是本分支新增的排障入口，但 `windows-package.bat` 没有复制它，也没有复制文档列出的
`windows-stop.bat`。打包脚本还缺少逐条 `copy` 错误检查，且把配置文件复制到自身。CI 未真正执行打包脚本。

建议：补齐复制清单，逐项检查错误码，避免复制到自身；CI 生成包后断言必需文件集合。

### P2-2：哈希清单覆盖不足

`windows-verify-package.ps1` 只检查清单至少 5 项，没有强制 `app/offline-asr.jar`、模型、tokens、FFmpeg、Java
运行时都在清单中；配置文件、启动脚本和 WinSW 未纳入哈希；JRE 只哈希 `java.exe`，不覆盖整个运行时文件集。

建议：定义必须精确覆盖的资产键；对 JRE 目录或归档整体做哈希；把配置和脚本纳入清单；明确清单不是签名，不能作为抗恶意篡改的边界。
