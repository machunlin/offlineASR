# 项目开发任务：跨平台离线中文语音转文字系统

> 文档版本：V2.2（2026-11-25）  
> 状态：开发基线；V1 的 Python/FastAPI 方案已被本文件的 Java/Spring Boot 方案替代，仅保留作历史参考。  
> 评审结论：可以进入分阶段开发，但必须先完成“官方 Java API + 指定模型 + 当前 macOS 原生库”的最小真实识别验证；Mac 验证不能替代目标 Windows 主机验证。

## 1. 项目目标

开发一个完全离线运行的普通话语音转文字系统。

用户通过 Windows Chrome 浏览器，使用连接在本机上的 USB 麦克风录音。录音结束后，浏览器将音频提交给本机 Spring Boot 后端，后端使用本地 ASR 模型完成语音识别，并返回完整文字。

核心要求：

1. 完全离线运行，正式部署完成后不依赖互联网。
2. 支持普通话语音识别，不需要提前输入提示词或预设词条。
3. 只需要录音结束后的完整文字，不需要实时流式识别。
4. 使用 CPU 推理，不依赖 GPU。
5. 浏览器能够通过 JavaScript 获取最终识别文字。
6. 系统需要具备完整的 Windows 单机部署能力。
7. 项目交付给技术支持工程师，由其在客户现场独立安装、调试和维护。
8. 必须提供完整、可执行的中文部署文档。

## 2. 已确定的技术路线

以下技术选型已经由项目负责人核验，不允许 Codex 擅自更换：

| 模块 | 技术 |
|---|---|
| ASR 引擎 | sherpa-onnx |
| 语音模型 | SenseVoiceSmall INT8 |
| Java 接口 | sherpa-onnx 官方 Java API |
| 后端 | Java 11 + Spring Boot 2.7.x |
| 构建 | Maven |
| Web 接口 | Spring MVC / REST API |
| 音频处理 | FFmpeg |
| 性能监控 | Spring Boot Actuator + Micrometer |
| 前端 | 原生 HTML + CSS + JavaScript |
| 浏览器 | Chrome |
| 推理设备 | CPU |
| 生产系统 | Windows x64 |

sherpa-onnx 官方 Java API 已确认支持 SenseVoice。

运行库版本基准：

- sherpa-onnx-jvm：v2.0.3
- sherpa-onnx-native-lib-osx-aarch64：macOS ARM64 开发环境
- sherpa-onnx-native-lib-win-x64：Windows x64 生产环境

经 2026-11-25 实测，v2.0.3 的上述 Java JAR 不发布到 Maven Central；必须从 sherpa-onnx 官方 GitHub Release 获取并校验 `sherpa-onnx-jvm-2.0.3.jar` 及各平台 `sherpa-onnx-native-lib-<platform>-2.0.3.jar`。Maven 项目应通过受版本控制的本地 `lib/` 目录或企业内部制品库引用这些官方资产，不能声明不存在的 Maven Central 坐标。

使用官方 API 和官方原生动态库，不通过 Python 中转，不自行开发 JNI。

注意：上述版本是项目基准。实际构建前检查官方发布资产、Maven Central 中的版本和平台兼容性。如果基准版本存在实际问题，先记录证据并停止相关变更，不得静默更换方案。

## 4. 生产运行环境

客户现场是一台 Windows 迷你主机，不是独立服务器。

硬件配置：

- CPU：Intel Core i7 第七代
- 内存：16GB，最大可扩展到24GB
- USB 接口
- 2个 RS232 串口
- 主机连接 USB 麦克风
- 无独立 GPU
- Windows x64 操作系统
- Chrome 浏览器安装在同一台主机上

### 4.1 单机部署要求

Windows 主机同时承担：

- 应用运行环境
- Spring Boot 后端
- Chrome 浏览器
- USB 麦克风采集
- ASR 模型 CPU 推理

前端和后端必须部署在同一台主机上。

默认访问地址：

http://127.0.0.1:8080

默认 Spring Boot 只绑定 127.0.0.1，不开放局域网访问。

浏览器通过：

navigator.mediaDevices.getUserMedia()

获取本机 USB 麦克风。

禁止开发 Java 麦克风采集模块。

禁止设计远程浏览器访问服务器麦克风的架构。

禁止引入不必要的网络服务、数据库、消息队列和 Docker。

### 4.2 硬件适配

1. 以16GB内存作为标准运行环境。
2. 默认 CPU 推理线程数为2，支持通过配置文件调整。
3. 不使用 GPU。
4. 记录目标机器实际 CPU 型号。
5. 不得将所有第七代 i7 视为相同性能。
6. 必须在目标 Windows 机器上测试实际推理性能。
7. 不得虚构性能指标或承诺未经测试的识别速度。

RS232 接口与第一版语音识别无关，不需要实现串口功能，但不得占用或干扰串口设备。

## 5. 跨平台设计

开发环境为 macOS ARM64，生产环境为 Windows x64。

必须分别使用对应平台的 sherpa-onnx 原生库。

macOS ARM64：

- sherpa-onnx-jvm
- sherpa-onnx-native-lib-osx-aarch64

Windows x64：

- sherpa-onnx-jvm
- sherpa-onnx-native-lib-win-x64

要求：

1. Java 业务代码保持跨平台。
2. Maven Profile 管理不同平台的原生依赖。
3. 提供 macos-arm64 和 windows-x64 两个 Profile。
4. 默认开发环境使用 macOS ARM64。
5. Windows 生产包使用 Windows x64。
6. 不得把 macOS 动态库打包到 Windows 部署包。
7. 不得把 Windows DLL 打包到 macOS 开发包。
8. 检查 JNI 动态库是否能正确加载。
9. 检查 Windows 运行时依赖是否完整。
10. 验证 Spring Boot 可执行 JAR 对原生依赖的加载方式。

如果官方 Maven 原生依赖的打包或加载机制与预期不一致，应采用官方支持的加载方式，不得仅为了构建成功而忽略运行时问题。

## 6. ASR 模型管理

使用 SenseVoiceSmall INT8。

模型文件和配置以官方发布资产为准，不要自行猜测模型文件名或下载链接。

要求：

1. 使用官方模型。
2. 使用 INT8 量化版本。
3. 模型文件放在独立 models 目录。
4. 模型路径通过 application.yml 配置。
5. 不将模型文件写死在 Java 代码中。
6. Spring Boot 启动时加载模型一次。
7. 后续请求复用已加载模型。
8. 默认 CPU 推理。
9. 支持配置 CPU 线程数。
10. 正确处理模型缺失、模型损坏、JNI 加载失败等问题。
11. 启动日志输出模型名称、模型路径、模型加载时间、推理设备和线程数。

禁止每次请求重新加载模型。

禁止调用云端模型。

禁止要求用户提前配置识别提示词。

## 7. 系统架构

整体处理流程：

Chrome 浏览器
→ USB 麦克风
→ MediaRecorder 录音
→ HTTP POST 上传
→ Spring Boot 接收音频
→ FFmpeg 解码
→ 统一转换为16kHz、单声道、Float32 PCM
→ sherpa-onnx Java API
→ SenseVoiceSmall INT8
→ CPU 推理
→ 返回识别文字
→ JavaScript 回调。

### 7.1 音频处理

浏览器可能产生不同的音频格式。

至少考虑：

- WebM / Opus
- MP4 / AAC
- WAV

要求：

1. 根据浏览器实际录音格式识别输入容器。
2. 使用 FFmpeg 解码。
3. 统一输出16kHz。
4. 统一为单声道。
5. 统一为 Float32 PCM。
6. 正确处理音频采样率和数据类型。
7. 检查 FFmpeg 执行状态和错误输出。
8. 防止临时文件残留。
9. 音频处理失败时返回明确错误。
10. 不将音频永久保存。

### 7.2 请求限制

建议初始配置：

- 单文件最大50MB。
- 单次录音最长10分钟。
- 同一时刻限制推理并发。
- 默认单路推理。
- 提供可配置的请求超时。
- 对异常输入进行校验。

所有限制必须配置化，不能散落在代码中。

## 9. REST API 设计

### 9.1 POST /api/asr

上传音频并执行语音识别。

请求：

multipart/form-data

参数：

- file：音频文件

响应：

{
  "success": true,
  "text": "今天的天气非常不错",
  "audioDuration": 3.5,
  "decodeTime": 0.12,
  "inferenceTime": 0.82,
  "totalTime": 1.05
}

失败时返回：

- success
- errorCode
- message

不要将 Java 异常堆栈直接返回给浏览器。

### 9.2 GET /api/asr/health

返回：

- applicationStatus
- modelLoaded
- modelName
- modelVersion
- inferenceDevice
- inferenceThreads
- ffmpegAvailable
- uptime

### 9.3 监控接口

提供：

- /actuator/health
- /actuator/metrics

只开放必要监控信息，不暴露敏感系统信息。

## 18. V2.1 评审补充与实施约束

本节是对前述需求的可执行化解释；如与此前模糊表述存在冲突，以本节为准。

### 18.1 唯一技术基线与版本核验

1. 本项目唯一实现基线为 Java 11、Spring Boot 2.7.x、Maven、sherpa-onnx 官方 Java API、SenseVoiceSmall INT8、FFmpeg、原生 HTML/CSS/JavaScript。不得混用 V1 中的 Python、FastAPI 或 Conda 方案。Spring Boot 3.x 的最低 Java 版本为 17，因本项目采用 Java 11，不得引入 Spring Boot 3.x。
2. `sherpa-onnx-jvm` v2.0.3 及平台原生库的 Maven 坐标、实际可用版本、传递依赖、平台 classifier 和 Java API，必须以 Maven Central 与 sherpa-onnx 官方发布资产的实际查询结果为准。
3. 如果基准版本不存在、未提供 macOS ARM64 或 Windows x64 原生库，或其 API / 加载方式不能满足本规范，必须在 `docs/验证记录.md` 中记录查询日期、来源链接、报错或差异；停止受影响的实现项并提交处理建议，不得静默替换版本、模型或引擎。
4. 模型仅接受 sherpa-onnx 官方发布的 `SenseVoiceSmall INT8` 对应资产。下载完成后在交付记录中保存发布页 URL、归档文件名、下载日期、必要文件清单和 SHA-256；模型文件本身不提交版本库。

### 18.2 启动、模型生命周期与并发

1. 应用启动阶段必须按顺序校验配置、模型必需文件、FFmpeg 可执行性和 JNI / ONNX Runtime 原生库加载；任一项失败时健康检查返回未就绪，应用日志记录可操作原因，但 HTTP 响应不得暴露绝对路径、堆栈或原始音频内容。
2. 模型在 Spring 容器生命周期中只创建一次，并由识别服务复用；禁止请求级创建识别器或重新加载模型。应用关闭时必须释放模型相关资源。
3. 首期使用可配置的单路推理闸门，默认只允许一个推理任务进入模型。闸门获取超时、解码超时、推理超时和整个请求超时均需有明确错误码；不得以无限排队或无限等待掩盖资源耗尽。
4. 默认推理线程数为 2，必须是正整数配置。线程数影响速度与系统资源，不承诺不同第七代 i7 的相同性能。

### 18.3 API、错误和可观测性契约

1. 每个 `/api/asr` 请求生成或接收一个格式受限的请求 ID，并在响应、日志和 Micrometer 标签中关联；日志不得含识别文本、音频内容、用户文件名或本机绝对路径。
2. 成功响应字段固定为 `success`、`requestId`、`text`、`audioDuration`、`decodeTime`、`inferenceTime` 和 `totalTime`。时间单位均为秒，数值为非负小数。
3. 失败响应统一为：

```json
{
  "success": false,
  "requestId": "...",
  "errorCode": "AUDIO_DECODE_FAILED",
  "message": "音频解码失败，请重新录音后重试"
}
```

4. 最小错误语义：缺少文件、空文件或非法 multipart 为 `400 INVALID_REQUEST`；上传大小超过限制为 `413 FILE_TOO_LARGE`；不支持或不能识别的媒体为 `415 UNSUPPORTED_MEDIA_TYPE`；可识别但无法解码、无有效音频或音频过长为 `422 AUDIO_DECODE_FAILED` / `AUDIO_DURATION_EXCEEDED`；模型不可用为 `503 SERVICE_NOT_READY`；阶段或总处理超时为 `504 PROCESSING_TIMEOUT`；其余受控识别失败为 `500 ASR_FAILED`。
5. `/api/asr/health` 必须明确 `applicationStatus`、`modelLoaded`、`modelName`、`inferenceDevice`、`inferenceThreads`、`ffmpegAvailable` 和 `uptime`。仅在本机绑定下开放 `/actuator/health`；`/actuator/metrics` 默认不对浏览器页面暴露，并在部署说明中给出本机诊断开启方式。

### 18.4 音频处理、安全与清理边界

1. 仅凭扩展名或客户端 MIME 类型不得决定音频格式。后端应将上传内容写入项目内受控的 `temp/` 唯一目录，由 FFmpeg 实际探测和解码为 16 kHz、单声道、Float32 PCM。
2. FFmpeg 必须以参数数组启动，不得拼接来自客户端的 shell 命令；必须捕获退出码和受限长度的错误输出，并设置解码时限。
3. 解码后根据真实采样数 / 采样率计算音频时长，作为最长录音时长的最终判断依据。文件大小限制在读取阶段执行，时长限制在解码阶段执行，二者均可由配置覆盖。
4. 请求成功、识别失败、客户端取消、超时或异常时，临时输入和输出均须在 `finally` 中删除。启动清理只允许处理项目 `temp/` 下本应用生成的历史临时文件，严禁广泛删除用户目录或系统临时目录。

### 18.5 浏览器状态与 JavaScript 接入契约

1. 前端录音状态固定为“空闲 → 申请权限 → 录音中 → 上传/识别中 → 成功或失败 → 空闲”；录音中仅允许停止或取消，上传/识别中禁止再次提交。
2. 录音开始前才调用 `getUserMedia`，停止、取消和失败后均关闭全部 MediaStream track；禁止后台录音或上传未由用户在本次操作录制的音频。
3. 优先从 Chrome 支持的 `MediaRecorder` MIME 类型中选择 WebM/Opus；服务端仍以 FFmpeg 实际结果为准。录音到达配置的最长时长时自动停止。
4. `OfflineASR.recognize(audioBlob)` 对同一次调用只发起一次 HTTP 请求，成功时 resolve 一个包含文本与耗时字段的结果对象，失败时 reject 至少含 `code` 和 `message` 的错误对象。
5. 对一次成功结果，若定义了 `onSpeechText(text)` 则调用一次，并派发一次 `asr-result` 事件；事件最小载荷为 `{ detail: { text, requestId } }`，可额外提供耗时字段，但不得含音频数据。Promise、回调和事件是同一结果的三种观察方式，不得由其中任一方式再次触发识别。

### 18.6 跨平台构建与交付边界

1. Maven 必须提供 `macos-arm64` 和 `windows-x64` Profile；Java 业务代码保持平台无关。每个 Profile 只解析本平台官方原生依赖，产物检查不得包含另一平台的原生库。
2. 在 macOS 上可验证 Java 编译、单元测试、macOS 原生加载、模型加载、HTTP 接口和本机 Chrome 流程；不能据此宣称 Windows DLL、Windows 服务、USB 麦克风、Visual C++ Runtime、目标 CPU 性能或断网部署已通过。
3. Windows 包采用可复制的目录布局：应用 JAR、经过验证的 Windows x64 Java Runtime、模型、FFmpeg、配置、日志和脚本均来自同一发布记录。若采用 WinSW，须在部署文档中锁定来源、版本、二进制 SHA-256、服务名、工作目录、日志位置、重启策略及卸载方式。
4. Windows 安装、升级和卸载脚本不得删除模型、日志或配置备份，除非操作人员明确选择该范围；默认绑定 `127.0.0.1:8080`，不开放局域网。
