# 开发协作与代码提交规范

## 1. Git 操作

1. 每次准备提交前，先 fetch 远端最新代码，并读取目标分支最新 HEAD。
2. 确认本地工作基于最新远端提交；若远端有新提交，先同步并处理冲突，不能覆盖他人或用户已有改动。
3. 每完成一个可独立验证的工作步骤，立即提交一次，避免多个无关改动混在一个提交中。
4. 提交说明尽量使用中文，准确描述本次改动，不使用含糊的“update”“fix”。
5. 默认只在当前任务分支提交；未经明确授权，不修改 master、不合并分支、不强制推送、不重写历史。
6. 提交后核验分支 HEAD、提交文件列表和 CI 结果；未实际运行的测试不得声称通过。

## 2. 中文表达约定

- 日志内容、提交说明、文档、代码注释和脚本注释尽量使用中文。
- 类名、方法名、变量名、配置键、API 路径、协议字段和标准技术名词按项目既有规范使用英文。
- 注释解释业务意图、关键约束和不明显的实现原因，不为显而易见的代码重复写注释。

## 3. 音频录制与诊断

- WebM 是容器格式，常见浏览器录音编码为 Opus。容器和编码可被识别，不代表其中包含有效语音。
- 对录音文件必须实际解码检查；若 PCM 的 RMS=0 且峰值=0，则文件为数字静音，不能归因于播放器不兼容。
- 通过 requestId 关联上传日志、FFmpeg 解码日志和音频统计。重点核对采样率、时长、RMS、峰值和削波样本数。
- 若上传文件可解码但 RMS/峰值均为 0，优先检查浏览器麦克风权限、输入设备选择、操作系统麦克风隐私/静音状态，以及 MediaStreamTrack 的 muted、readyState；不要先修改 ASR 模型或 FFmpeg 参数。
- 录音验收必须包含实际说话并回放录音文件，不能只以文件生成成功或 HTTP 上传成功作为通过标准。

## 4. 变更验证

- 修改前先读取最新代码和现有测试，保持兼容性并保留用户已有改动。
- 新增行为应补充自动化测试；真实硬件、麦克风和目标 Windows 环境需单独标注验证边界。
- 修改脚本时，交付完整可执行版本。
